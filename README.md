# Test Cargo Task

Тестовое задание «Заправка в рейсе».

Прототип приложения для безналичной заправки грузового транспорта в счёт лимита перевозчика. Основной сценарий позволяет водителю найти подходящую АЗС, выбрать топливо и колонку, оформить заказ, отслеживать заправку и получить итог с фактически списанной суммой.

## 1. Расхождения в материалах

| № | Расхождение | Решение в прототипе |
|---|---|---|
| 1 | В макете и разговоре общий лимит составляет 20 000 ₽, API возвращает 15 000 ₽. | Используем `limitTotal` из API — 15 000 ₽. |
| 2 | Макет показывает доступный остаток 12 450 ₽, разговор — около 9 300 ₽, API — 9 340 ₽. | Отображаем актуальный `limitLeft` из API. |
| 3 | Макет содержит номер прицепа, но `getTrip()` возвращает только тягач и не содержит данных о прицепе. | Не показываем номер прицепа, поскольку API его не предоставляет. |
| 4 | Диспетчер разрешает отмену до половины заправки, API разрешает отмену только в статусах `accepted` и `waiting_nozzle`. | Ориентируемся на фактический статус API. После начала налива отмена недоступна. |
| 5 | Диспетчер говорит о 40 секундах на установку пистолета, API не поддерживает отдельное подтверждение установки и использует собственную временную модель. | Не реализуем неподдерживаемый механизм подтверждения пистолета. |
| 6 | Диспетчер считает разницу в 1 копейку округлением, но API отклоняет изменение цены, превышающее 0,001 ₽. | Используем точную цену API. При `PRICE_CHANGED` показываем новые условия и просим подтверждение. |
| 7 | Диспетчер говорит об отдельной заправке рефрижератора с использованием общего лимита, но API не содержит признака назначения топлива. | Не реализуем раздельный учёт заправок тягача и рефрижератора. |


## 2. Решение для владельца парка

### Основное продуктовое решение: планирование заправок вместе с маршрутом

1. Предлагается заранее формировать маршрут рейса с оптимальными остановками для заправки.
2. Для построения маршрута используется существующий картографический сервис, собственную навигацию разрабатывать не требуется.
3. При расчёте учитываются характеристики автомобиля: расход топлива, вместимость бака и текущий запас топлива.
4. Система получает АЗС вдоль маршрута и исключает станции с неподходящим топливом или чрезмерным отклонением от пути.
5. Алгоритм подбирает последовательность остановок, минимизируя общую стоимость топлива и дополнительные затраты на отклонение от маршрута.
6. При расчёте учитываются ограничения АЗС на одну заправку, запас топлива для достижения следующей остановки и общий бюджет рейса.
7. Водитель получает готовый план с адресами АЗС, рекомендуемыми объёмами заправки и ожидаемыми затратами.
8. При недоступности станции или изменении маршрута план пересчитывается; водитель сохраняет возможность выбрать альтернативу.
9. За две недели можно реализовать MVP на основе существующего маршрутизатора и ограниченного алгоритма оптимизации для одного рейса.
10. В рамках данного тестового прототипа используется упрощённый подход: рекомендация выгодной АЗС поблизости, поскольку FakeApi не предоставляет данные о маршруте и характеристиках расхода топлива автомобиля.

### Отвергнутые альтернативы

**1. Рекомендация самой дешёвой АЗС поблизости.**

Не учитывает весь маршрут и будущие остановки. Локально дешёвая заправка не обязательно обеспечивает минимальные затраты на протяжении всего рейса. Этот подход используется в прототипе только как упрощённая демонстрация выбора АЗС.

**2. Жёсткое ограничение суммы одной заправки.**

Не учитывает реальную потребность автомобиля в топливе и может привести к дополнительным остановкам. Кроме того, ограничение само по себе не помогает выбирать выгодные АЗС.

### Метрика оценки результата

**Средние расходы на топливо на 100 км пробега.**

Через месяц сравниваем показатель с базовым периодом на сопоставимых рейсах и автомобилях. Если расходы не снизились, гипотеза об эффективности маршрутного планирования не подтвердилась.


## 3. Архитектура и реализация прототипа

### 3.1. Структура проекта

Прототип реализован на чистом HTML, CSS и JavaScript без использования фреймворков и сторонних библиотек.

Используются два файла приложения:

- `index.html` — структура приложения, стили и HTML-шаблоны экранов.
- `app.js` — состояние приложения, взаимодействие с API, обработка пользовательских действий и логика сценария.

`fake-api.js` — предоставленный в задании эмулятор API. Его исходный код не изменялся.

Все экраны создаются на основе HTML-шаблонов, находящихся в `index.html`. JavaScript подставляет в них данные и управляет переходами между состояниями приложения.

Для обработки действий используется делегирование событий: обработчик на уровне приложения обслуживает нажатия на статические и динамически созданные элементы.

### 3.2. Экраны приложения

| Экран | Назначение |
|---|---|
| Главный | Информация о рейсе, тягаче и доступном лимите. |
| Выбор топлива | Доступные виды топлива, количество подходящих АЗС и минимальная цена. |
| Выбор АЗС | Сравнение станций по цене и расстоянию. |
| Выбор колонки | Список колонок, их статусы и совместимость с выбранным топливом. |
| Ввод объёма | Количество литров, ограничения АЗС и предварительная стоимость. |
| Проверка заказа | Сводная информация о заправке и возможность изменить выбранные параметры. |
| Выполнение заправки | Статус заказа, заказанный и фактически залитый объём, цена и сумма холда. |
| Итог | Результат заправки, фактическое списание и остаток лимита. |
| Загрузка и ошибки | Отображение состояния запросов и ошибок с возможностью повторить операцию. |

Для отдельных элементов используются дополнительные шаблоны карточек топлива, АЗС, групп станций и колонок.

### 3.3. Поиск и выбор АЗС

После перехода с главного экрана приложение параллельно получает координаты водителя и список доступных АЗС через `getDriverLocation()` и `getStations()`.

Расстояние между водителем и станциями рассчитывается по координатам с использованием формулы гаверсинусов. В расчёте используется расстояние по прямой, а не дорожный маршрут.

В радиусе 30 км приложение определяет доступные виды топлива. Для каждого вида показывает количество подходящих АЗС и минимальную цену за литр.

После выбора топлива формируется список станций, предлагающих выбранный вид топлива:

- АЗС с минимальной ценой показывается первой и выделяется цветом.
- Остальные станции распределяются по группам: до 10 км, 10–20 км и 20–30 км.
- Внутри каждой группы станции сортируются по цене, а при одинаковой цене — по расстоянию.

После выбора АЗС приложение вызывает `getStation(id)` и получает подробную информацию о топливе, ценах, колонках и ограничениях по объёму.

### 3.4. Выбор колонки и объёма

На экране выбора колонки отображаются её номер, статус и доступные виды топлива.

Выбрать можно только свободную колонку, совместимую с ранее выбранным топливом. Занятые, неисправные и несовместимые колонки недоступны для выбора.

Для АЗС бренда «Колесо» реализовано дополнительное отображение буквенных обозначений первых четырёх колонок (А, Б, В, Г) вместе с номерами, возвращаемыми API. Для остальных АЗС отображаются только номера колонок, поскольку в предоставленных материалах отсутствует информация об их буквенных обозначениях. При появлении таких данных соответствующая логика будет расширена.

После выбора колонки водитель указывает объём топлива.

Приложение проверяет:

- минимальный объём, разрешённый АЗС;
- максимальный объём, разрешённый АЗС;
- соответствие стоимости заправки доступному остатку лимита.

При изменении количества литров предварительная стоимость пересчитывается непосредственно на экране.

Затем открывается экран проверки заказа. На нём отображаются АЗС, топливо, колонка, объём, цена за литр и общая стоимость. Каждый из выбранных параметров можно изменить до подтверждения.

### 3.5. Создание заказа и холд

Перед отправкой заказа приложение формирует запрос со следующими параметрами:

- идентификатор АЗС;
- номер колонки;
- код топлива;
- заказанный объём;
- цена за литр;
- уникальный `clientRequestId`.

До отправки запрос и выбранные параметры сохраняются в `localStorage`.

После подтверждения вызывается `startFueling()`. API проверяет возможность заправки, актуальность цены, ограничения по объёму и доступный лимит.

При успешном создании заказа необходимая сумма блокируется на лимите. Она отображается в приложении как холд.

После получения ответа приложение сохраняет `fuelingId` и открывает экран выполнения заправки.

Если фактически залитый объём оказывается меньше заказанного, API рассчитывает списание по фактическому объёму, а неиспользованная часть холда возвращается на лимит. При отмене заправки до завершения налив не учитывается, и холд возвращается полностью.

### 3.6. Обработка ошибок при создании заказа

При отправке заказа приложение отдельно обрабатывает следующие ошибки API:

| Ошибка | Поведение приложения |
|---|---|
| `NETWORK_ERROR` | Сохраняется исходный запрос. Пользователь может повторить отправку с тем же `clientRequestId`. |
| `PRICE_CHANGED` | Новая цена сохраняется в заказе и отображается на экране проверки для повторного подтверждения. |
| `PUMP_BUSY` | Колонка помечается занятой, ожидающий заказ удаляется, пользователь возвращается к выбору колонки. |
| `FUEL_NOT_AVAILABLE` | Выбранное топливо удаляется из списка доступных на этой колонке, пользователь возвращается к выбору колонки. |
| `INVALID_LITERS` | Ограничения объёма обновляются по данным API, пользователь возвращается к вводу литров. |
| `LIMIT_EXCEEDED` | Обновляется доступный остаток лимита, если API передал новое значение, пользователь возвращается к вводу объёма. |

Ожидающий заказ очищается при ошибках, после которых пользователь должен изменить параметры заправки.

Остальные ошибки попадают в общий обработчик: приложение отображает сообщение API и предлагает повторить отправку.

### 3.7. Выполнение заправки, отслеживание и отмена

После создания заказа приложение отображает его текущий статус:

- `accepted` — заказ принят;
- `waiting_nozzle` — ожидание установки пистолета;
- `fueling` — выполняется налив.

Приложение периодически вызывает `getFueling(id)` для обновления состояния заказа. Следующий запрос планируется через 2 секунды после завершения предыдущего. При сетевой ошибке отображается сообщение, после чего запрос планируется повторно.

Водитель также может вручную запросить обновление статуса.

Кнопка отмены отображается только в статусах `accepted` и `waiting_nozzle`.

Если пользователь нажимает отмену во время выполнения запроса обновления статуса, приложение сохраняет намерение отменить заказ. После завершения текущего запроса проверяется актуальное состояние заправки, затем отправляется запрос на отмену, если она ещё допустима.

Окончательное решение принимает API через `cancelFueling(id)`. Если налив уже начался, API отклоняет отмену, а приложение сообщает об этом пользователю и продолжает отслеживание.

При завершении или отмене заказа приложение переходит к обновлению данных рейса.

### 3.8. Итог заправки

После получения конечного статуса приложение запрашивает актуальную информацию о рейсе через `getTrip()`.

Итоговый экран отображает:

- фактически залитый объём;
- цену за литр;
- фактически списанную сумму;
- остаток лимита после завершения операции.

При отмене отображается нулевой объём и нулевая сумма списания.

Если обновить информацию о рейсе не удаётся, приложение не показывает потенциально устаревший остаток лимита. Вместо этого отображается сообщение о завершении заправки и предлагается повторить получение данных.

Итоговый экран открывается после успешного обновления информации о рейсе.

### 3.9. Сохранение состояния и восстановление после потери связи

Для сохранения ожидающего заказа используется `localStorage`. Запись приложения хранится под ключом `zapravka.pendingFueling`.

Перед отправкой запроса сохраняются параметры заказа и уникальный `clientRequestId`.

Это необходимо для обработки ситуации, когда API успел создать заправку, но ответ потерялся при передаче. При повторной отправке используется тот же идентификатор. FakeApi поддерживает идемпотентность по `clientRequestId` и возвращает ранее созданный заказ вместо создания нового.

После получения успешного ответа сохраняется `fuelingId`, который используется для восстановления статуса заправки.

При повторном открытии приложения возможны следующие сценарии:

1. Если сохранён заказ с `fuelingId`, приложение получает его состояние через `getFueling()`. При ошибке запроса отображается сообщение с возможностью повторить восстановление.
2. Если заказ сохранён, но `fuelingId` ещё не получен, приложение повторно отправляет сохранённый запрос с прежним `clientRequestId`.
3. Если локальных данных о заказе нет, приложение вызывает `getActiveFueling()` для поиска незавершённой заправки.
4. Если активный заказ найден, приложение сохраняет его идентификатор и открывает экран отслеживания.
5. Если `getActiveFueling()` завершается ошибкой, приложение показывает экран проверки активной заправки и предлагает повторить запрос. Начать новую заправку до успешной проверки нельзя.

После завершения или отмены заказа сохранённая запись ожидающего заказа остаётся доступной до выбора действия «Новая заправка». При выборе этого действия состояние текущего заказа очищается и приложение возвращается на главный экран.


## 4. Запуск проекта

Для запуска приложения не требуется установка дополнительных библиотек или сборка проекта.

В одной директории должны находиться три файла:

- `index.html`
- `app.js`
- `fake-api.js`

Для запуска необходимо открыть терминал в директории проекта и выполнить команду:

```powershell
python -m http.server 8000
```

После запуска локального сервера открыть в браузере адрес:

`http://localhost:8000/`

Приложение работает непосредственно в браузере. Все запросы выполняются к предоставленному FakeApi. Состояние FakeApi и сохранённый ожидающий заказ приложения хранятся в `localStorage`.
