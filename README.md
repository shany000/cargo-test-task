# Test Cargo Task

Тестовое задание «Заправка в рейсе».

## 1. Расхождения в материалах

| № | Расхождение | Решение в прототипе |
|---|---|---|
| 1 | В макете и разговоре общий лимит составляет 20 000 ₽, API возвращает 15 000 ₽. | Используем `limitTotal` из API — 15 000 ₽. |
| 2 | Макет показывает доступный остаток 12 450 ₽, разговор — около 9 300 ₽, API — 9 340 ₽. | Отображаем актуальный `limitLeft` из API. |
| 3 | Макет содержит номер прицепа, но `getTrip()` возвращает только тягач и не содержит данных о прицепе. | Не показываем номер прицепа, поскольку API его не предоставляет. |
| 4 | Диспетчер разрешает отмену до половины заправки, API разрешает отмену только в статусах `accepted` и `waiting_nozzle`. | Ориентируемся на фактический статус API. После начала налива отмена недоступна. |
| 5 | Диспетчер говорит о 40 секундах на установку пистолета, API не поддерживает отдельное подтверждение установки и использует собственную временную модель. | Не реализуем неподдерживаемый механизм подтверждения пистолета. |
| 6 | Диспетчер считает разницу в 1 копейку округлением, но API отклоняет изменение цены, превышающее 0,001 ₽. | Используем точную цену API. При `PRICE_CHANGED` показываем новые условия и просим подтверждение. |
| 7 | Диспетчер говорит об отдельной заправке рефрижератора с использованием общего лимита, но API не содержит признака назначения топлива. | Не реализуем раздельный учёт заправок тягача и рефрижератора. |


## 2. Решение для владельца парка

### Основное продуктовое решение: планирование заправок вместе с маршрутом

1. Предлагается заранее формировать маршрут рейса с оптимальными остановками для заправки.
2. Для построения маршрута используется существующий картографический сервис, собственную навигацию разрабатывать не требуется.
3. При расчёте учитываются характеристики автомобиля: расход топлива, вместимость бака и текущий запас топлива.
4. Система получает АЗС вдоль маршрута и исключает станции с неподходящим топливом или чрезмерным отклонением от пути.
5. Алгоритм подбирает последовательность остановок, минимизируя общую стоимость топлива и дополнительные затраты на отклонение от маршрута.
6. При расчёте учитываются ограничения АЗС на одну заправку, запас топлива для достижения следующей остановки и общий бюджет рейса.
7. Водитель получает готовый план с адресами АЗС, рекомендуемыми объёмами заправки и ожидаемыми затратами.
8. При недоступности станции или изменении маршрута план пересчитывается; водитель сохраняет возможность выбрать альтернативу.
9. За две недели можно реализовать MVP на основе существующего маршрутизатора и ограниченного алгоритма оптимизации для одного рейса.
10. В рамках данного тестового прототипа используется упрощённый подход: рекомендация выгодной АЗС поблизости, поскольку FakeApi не предоставляет данные о маршруте и характеристиках расхода топлива автомобиля.

### Отвергнутые альтернативы

**1. Рекомендация самой дешёвой АЗС поблизости.**

Не учитывает весь маршрут и будущие остановки. Локально дешёвая заправка не обязательно обеспечивает минимальные затраты на протяжении всего рейса. Этот подход используется в прототипе только как упрощённая демонстрация выбора АЗС.

**2. Жёсткое ограничение суммы одной заправки.**

Не учитывает реальную потребность автомобиля в топливе и может привести к дополнительным остановкам. Кроме того, ограничение само по себе не помогает выбирать выгодные АЗС.

### Метрика оценки результата

**Средние расходы на топливо на 100 км пробега.**

Через месяц сравниваем показатель с базовым периодом на сопоставимых рейсах и автомобилях. Если расходы не снизились, гипотеза об эффективности маршрутного планирования не подтвердилась.


## 3. Архитектура прототипа

Прототип реализован на чистом HTML, CSS и JavaScript без использования фреймворков и сторонних библиотек.

Приложение состоит из двух файлов:

- `index.html` — структура приложения, HTML-шаблоны экранов и стили.
- `app.js` — состояние приложения, работа с API, обработка действий пользователя и логика переходов между экранами.

`fake-api.js` — предоставленный в задании эмулятор API. Его исходный код не изменялся.

### 3.1. Структура index.html

В `index.html` находятся следующие экраны и шаблоны:

| Шаблон | Назначение |
|---|---|
| `home-screen` | Главный экран: информация о рейсе, тягаче и доступном лимите. |
| `fuels-screen` | Выбор вида топлива. Показывает количество подходящих АЗС и минимальную цену за литр в радиусе 30 км. |
| `stations-screen` | Выбор АЗС с учётом выбранного топлива. Самая выгодная станция выделяется отдельно, остальные группируются по расстоянию. |
| `station-card` | Карточка АЗС с расстоянием по прямой, адресом и ценой выбранного топлива. |
| `station-group` | Группа станций определённого диапазона расстояния. |
| `pumps-screen` | Выбор свободной колонки, совместимой с выбранным топливом. |
| `liters-screen` | Ввод объёма топлива, отображение ограничений АЗС и предварительной стоимости. |
| `review-screen` | Проверка выбранной АЗС, топлива, колонки, объёма и стоимости. Предусмотрено изменение каждого параметра. |
| `fueling-screen` | Отображение процесса заправки: текущего статуса, заказанного и фактически залитого объёма, цены и суммы холда. |
| `result-screen` | Итог заправки: фактический объём, списанная сумма и остаток лимита. |
| `message-screen` | Отображение состояния загрузки и ошибок API. |

Для отдельных элементов используются дополнительные шаблоны `fuel-option` и `pump-option`.

Для АЗС бренда «Колесо» реализовано дополнительное отображение буквенных обозначений первых четырёх колонок (А, Б, В, Г) вместе с номерами, возвращаемыми API. Для остальных АЗС отображаются только номера колонок, поскольку в предоставленных материалах отсутствует информация об их буквенных обозначениях. При появлении таких данных соответствующая логика будет расширена.

Все стили находятся внутри `index.html`.

### 3.2. Структура app.js

`app.js` отвечает за логику приложения и взаимодействие с пользователем.

Основные части:

- `state` — текущее состояние приложения, загруженные данные, выбранные параметры и информация о заказе.
- `money()` — форматирование денежных значений.
- `distance()` — расчёт расстояния между водителем и АЗС по координатам.
- `nearbyStations()` — получение списка АЗС в радиусе 30 км.
- `clone()`, `setField()` и `show()` — работа с HTML-шаблонами и заполнение их данными.
- `render...()` — функции отображения отдельных экранов.
- `load()` — выполнение асинхронных запросов к API, отображение состояния загрузки и обработка ошибок.
- `loadFuelOptions()` и `loadStation()` — загрузка информации, необходимой для выбора топлива и АЗС.
- `pumpName()` — формирование отображаемого названия колонки с учётом особенностей АЗС «Колесо».

Для обработки нажатий используется делегирование событий: один обработчик обслуживает действия на всех динамически создаваемых элементах.

Для создания и сопровождения заказа используются отдельные функции:

- `createPending()` — формирование запроса на заправку и сохранение его параметров перед отправкой.
- `submitFueling()` — отправка заказа через API и обработка результата.
- `refreshFueling()` — получение актуального состояния заправки.
- `schedulePolling()` — планирование автоматического обновления статуса.
- `cancelFueling()` — отправка запроса на отмену заправки.
- `finishFueling()` — завершение сценария, попытка обновления информации о рейсе и переход к итоговому экрану.
- `restoreOrder()` — восстановление сохранённого или активного заказа при повторном открытии приложения.
- `readPending()`, `restorePending()`, `savePending()` и `clearPending()` — чтение, восстановление, сохранение и удаление данных ожидающего заказа.
- `isFinished()` — проверка завершения или отмены заправки.

### 3.3. Пользовательский сценарий

Текущая последовательность экранов:

1. **Главный экран.** Показывает текущий рейс, автомобиль и доступный остаток лимита.
2. **Выбор топлива.** Пользователь выбирает подходящий вид топлива. Для каждого вида отображаются минимальная цена и количество АЗС, предлагающих его в радиусе 30 км.
3. **Выбор АЗС.** Станции сравниваются по цене выбранного топлива. Самая выгодная находится первой и выделяется цветом. Остальные станции распределяются по расстоянию по прямой: до 10 км, 10–20 км и 20–30 км. Внутри групп сортировка выполняется по цене.
4. **Выбор колонки.** Отображаются статусы колонок и доступные виды топлива. Выбрать можно только свободную колонку, совместимую с выбранным топливом. Для АЗС «Колесо» дополнительно показываются буквенные обозначения колонок.
5. **Ввод объёма.** Пользователь указывает количество литров. Проверяются минимальный и максимальный объём, установленные АЗС, и доступный остаток лимита. Рассчитывается предварительная стоимость.
6. **Проверка выбора.** Отображаются все выбранные параметры. Пользователь может изменить АЗС, топливо, колонку или объём без необходимости начинать сценарий заново.
7. **Подтверждение заказа.** Перед отправкой запроса приложение формирует заказ, присваивает ему уникальный идентификатор `clientRequestId` и сохраняет параметры в `localStorage`.
8. **Создание и выполнение заправки.** Через `startFueling()` приложение отправляет заказ в API. При успешном создании API блокирует необходимую сумму на лимите. Приложение отображает статус заказа, заказанный объём и сумму холда.
9. **Отслеживание и отмена.** Приложение периодически запрашивает состояние заказа через `getFueling()`. Кнопка отмены отображается для статусов `accepted` и `waiting_nozzle`. Запрос на отмену может быть отклонён API, если налив уже начался. Кроме того, отправка отмены не выполняется, пока приложение загружает данные или уже выполняется запрос обновления статуса.
10. **Итог.** После завершения или отмены заправки отображаются фактически залитый объём, списанная сумма и остаток лимита.

### 3.4. Взаимодействие с API

Используются следующие методы FakeApi:

| Метод | Назначение |
|---|---|
| `getTrip()` | Получение информации о рейсе и лимите. |
| `getDriverLocation()` | Получение координат водителя. |
| `getStations()` | Получение списка АЗС и доступных цен на топливо. |
| `getStation(id)` | Получение подробной информации об АЗС: виды топлива, цены, колонки и ограничения по объёму. |
| `startFueling()` | Создание заказа на заправку. |
| `getFueling(id)` | Получение текущего состояния заказа. |
| `cancelFueling(id)` | Отмена заказа. |
| `getActiveFueling()` | Поиск незавершённой заправки. |

Получение местоположения и списка станций выполняется параллельно с помощью `Promise.all()`.

Для выбора топлива используются цены из списка АЗС. После выбора конкретной станции запрашивается её подробная информация, включая доступные виды топлива, колонки и ограничения по объёму.

При создании заказа приложение обрабатывает основные ошибки API:

- `NETWORK_ERROR` — сохраняет исходный запрос и позволяет повторить отправку с тем же `clientRequestId`.
- `PRICE_CHANGED` — обновляет цену в сохранённом запросе и возвращает пользователя на экран проверки заказа для подтверждения новых условий.
- `PUMP_BUSY` — отмечает колонку занятой, очищает ожидающий заказ и возвращает пользователя к выбору колонки.
- `LIMIT_EXCEEDED` — обновляет доступный остаток лимита, если API передал новое значение, очищает ожидающий заказ и возвращает пользователя к вводу объёма.

Остальные ошибки, в том числе `FUEL_NOT_AVAILABLE` и `INVALID_LITERS`, попадают в общий обработчик. Приложение отображает сообщение API и предлагает повторить отправку. Специального возврата к изменению топлива или объёма для этих ошибок в текущей реализации нет.

При ошибке загрузки рейса, списка АЗС или информации о выбранной станции пользователь получает сообщение и возможность повторить соответствующий запрос.

### 3.5. Обработка потери связи и восстановление заказа

Для сохранения состояния ожидающего заказа используется `localStorage`. Запись приложения хранится под ключом `zapravka.pendingFueling`.

Перед отправкой запроса приложение сохраняет его параметры и уникальный `clientRequestId`. Это позволяет повторить запрос после сетевой ошибки с тем же идентификатором.

FakeApi поддерживает идемпотентность создания заказов по `clientRequestId`: если заказ с таким идентификатором уже существует, повторный запрос возвращает ранее созданный заказ, а не создаёт новый.

После успешного создания заказа приложение сохраняет идентификатор заправки (`fuelingId`) и использует его для последующего получения статуса.

Во время выполнения заправки приложение запрашивает её состояние через `getFueling()`. Следующий запрос планируется через 2 секунды после завершения предыдущего. Если обновить статус не удалось, пользователь получает сообщение об ошибке, а приложение планирует повторный запрос.

При повторном открытии приложения восстановление зависит от сохранённого состояния:

- Если заказ содержит `fuelingId`, приложение запрашивает его состояние через `getFueling()`. Если запрос завершается ошибкой, отображается сообщение с возможностью повторить восстановление.
- Если запрос был сохранён, но `fuelingId` ещё не получен, приложение повторно отправляет его с прежним `clientRequestId`.
- Если локальных данных о заказе нет, приложение выполняет поиск активной заправки через `getActiveFueling()`. Если заказ найден, его идентификатор сохраняется, после чего открывается экран отслеживания.

Если запрос `getActiveFueling()` завершается ошибкой, текущая реализация не показывает отдельное сообщение и остаётся на главном экране.

После завершения или отмены заказа приложение пытается получить актуальную информацию о рейсе через `getTrip()`. При успешном ответе остаток лимита обновляется. Если запрос завершается ошибкой, приложение всё равно показывает итоговый экран, используя последнее сохранённое значение лимита.

Сохранённая запись ожидающего заказа удаляется при выборе действия «Новая заправка».

## 4. Запуск проекта

Для запуска приложения не требуется установка дополнительных библиотек или сборка проекта.

В одной директории должны находиться три файла:

- `index.html`
- `app.js`
- `fake-api.js`

Для запуска необходимо открыть терминал в директории проекта и выполнить команду:

```powershell
python -m http.server 8000
```

После запуска локального сервера открыть в браузере адрес:

`http://localhost:8000/`

Приложение работает непосредственно в браузере. Все запросы выполняются к предоставленному FakeApi. Состояние FakeApi и сохранённый ожидающий заказ приложения хранятся в `localStorage`.
